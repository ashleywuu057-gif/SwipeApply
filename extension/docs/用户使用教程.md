# 投简助手 ApplyKit 使用教程

适用版本：0.1.0。更新日期：2026-09-10。

当前版本包含 118 个单元测试和 52 个扩展端到端场景。测试覆盖本地演示、通用表单及 Moka、北森 Phoenix、飞书招聘 ATSX 适配器。

建议先在本地演示页面体验完整流程。Moka、北森 Phoenix 和飞书招聘 ATSX 已完成真实页面复验，其余网站仍需逐页核对，不应把通用适配理解为所有网站均已兼容。

## 1. 第一次启动：使用已有产物

先进入克隆后的项目根目录：

```bash
cd /path/to/ApplyKit
npm ci
npm run build
npm run demo
```

终端出现三个演示网址后，保持这个终端运行。它只负责提供本地测试网页；将来在真实招聘网页使用扩展时，不需要运行这个演示服务器。

如果提示端口 4173 已被占用，先打开下面的 basic 页面检查是否已有 ApplyKit 演示服务器在运行。有的话直接使用；不要随意改端口，因为当前演示适配器匹配的是 4173。

## 2. 在 Chrome 加载插件

1. 在 Chrome 地址栏输入 `chrome://extensions`。
2. 开启右上角「开发者模式」。
3. 点击「加载已解压的扩展程序」。
4. 选择下面的目录：

```text
<仓库目录>/dist
```

5. 在 Chrome 工具栏的拼图菜单中，把「投简助手 ApplyKit」固定到工具栏。

必须选择 `dist`，不要选择项目根目录，也不要选择 `.test-dist`。`.test-dist` 是增加了本地测试权限的自动化测试产物，不是日常使用的安装目录。

若选择目录时找不到它，在 macOS 文件选择窗口按 `Command + Shift + G`，粘贴上述完整路径并前往。

## 3. 导入演示履历

1. 点击工具栏中的投简助手图标。
2. 点击「履历管理」，打开扩展工作台。
3. 在「导入履历文件」选择：

```text
<仓库目录>/fixtures/profile.demo.json
```

4. 点击「校验并导入」。
5. 核对预览，确认显示的是「林示例」和虚构资料标记。
6. 点击「确认导入」。

导入后会自动成为当前版本。若已有多个履历版本，可在目标版本旁点击「设为当前版本」。

这个文件是虚构样例，只能在本地演示网页填写，不能用来投真实岗位。也不必现在导入 `applications.demo.json`：日常体验中的投递记录可以在后面的步骤自己创建。

## 4. 跑通第一张表单

打开：

[基础填写演示](http://127.0.0.1:4173/basic.html)

在这个网页上执行：

1. 点击 Chrome 工具栏上的投简助手图标。
2. 检查「当前履历」是演示版本，「当前网站」是 `127.0.0.1:4173`。
3. 点击「一键填写」。如果想先看识别结果，也可以先点「扫描页面」。
4. 第一次体验时先保持弹窗打开，等它显示「本轮填写结束」。
5. 查看网页上的控件，以及页面自己的「页面实际接收到的数据」面板。
6. 在弹窗点击「查看详情并处理待处理项」，打开结果工作台。

已有验收中，这张表单共 16 个逻辑字段，首次填写通常为：已填写 8、原值相同 2、保留原值 1、待处理 5。你修改过表单或履历后，计数可能变化。

表单默认的「上海」不会被直接覆盖，是预期行为。GitHub 缺失、生日需要确认、多意向岗位不能擅自选一个等情况也会留待处理，因此「不是全部变绿」不代表插件失败。

每次开始填写，都要先切换到目标招聘网页，再点击工具栏图标。仅打开扩展工作台，不等于已经授权它访问一个新的网页。

## 5. 体验多段教育和项目

打开：

[多段经历演示](http://127.0.0.1:4173/experience.html)

在该页面点击工具栏图标 →「一键填写」。重点检查：

- 硕士和本科的学校、专业、时间分别在正确区域。
- 年份和月份填写正确。
- 异步下拉框有实际选中结果。
- 项目区新增第二条项目，且没有重复新增。

已有验收中，此页 23 个字段均正确填写。再次运行时，应保留已存在的相同内容，不再额外添加一条重复项目。

## 6. 教插件记住陌生字段

打开：

[异常与规则学习演示](http://127.0.0.1:4173/edge-cases.html)

1. 在该页点击插件 →「一键填写」。
2. 打开结果详情，找到「联系信箱入口」。第一次它应是待处理。
3. 在该行的「选择履历中的源字段」下拉框选择邮箱。
4. 勾选「记住这个对应关系」。
5. 点击「应用到此字段」。
6. 看到「已填写并保存规则」后，确认原网页已经写入邮箱。
7. 刷新演示网页，使字段恢复初始状态；再次点击插件并填写。
8. 同样的字段现在应自动识别，无需再次选择源字段。

修正期间保留原网页，不要提前刷新，否则原运行中的字段定位可能失效。刷新后如果继续操作旧结果报错，重新扫描即可。

「记住对应关系」只能解决字段含义不明确的问题。iframe、无语义自定义控件、附件上传、声明或缺少精确日期，不能靠随意选一个源字段解决。

需要覆盖网页已有不同内容时，针对那一项勾选「允许覆盖网页已有内容」，再点击「应用到此字段」。不要为方便而把所有已有内容都覆盖。

## 7. 保存和更新投递记录

填写结果页下方如果识别出了公司和岗位，会显示「岗位候选（需人工核对）」。

1. 点击「用这些信息新建投递记录」。
2. 核对公司、岗位、地点、链接和使用的履历版本。
3. 填写下一步或备注，点击「保存记录」。
4. 没识别出岗位时，也可从工具栏「投递记录」进入，手动新增。

插件完成填写不会自动把记录变成「已投递」。在本地演示中：

1. 由你点击网页上的「提交演示申请」。
2. 确认演示页面出现成功提示。
3. 回到插件「投递记录」，在对应记录点击「我已手动提交并看到成功提示」。

真实投递也是这个顺序：先由你完成网站提交，再记录成功。后续在记录中修改笔试、面试、Offer 等状态。

相同岗位会出现已有记录提示。通常选择「打开已有记录」继续维护；只有确实是重新申请时才新建申请。

## 8. 换成自己的真实履历

当前版本的履历页只有导入、编辑已有版本、切换当前版本和导出，尚没有直接新建空白真实履历的按钮，也没有 PDF/Word 自动解析入口。

真实使用的路线是：

1. 按 ApplyKit 的原生 `applykit-profile` JSON 结构整理一份真实资料文件。
2. 使用独立的 profileId 和 profileVersionId；资料全部来自已确认事实，未知值保留 null。
3. 完成资料审阅后，来源使用 import/manual，状态为 user-reviewed。不能只修改虚构样例的标记便用于真实求职。
4. 在「履历管理」校验并导入，设为当前版本。
5. 以后普通修改可以在界面点击「编辑」→「保存为新版本」，不必每次重新制作 JSON。

旧的 Offer来了 JSON 格式和现有 Markdown 知识库不能直接导入当前版本，需要先做格式转换。ApplyKit 的结构可参考 [虚构格式样例](../fixtures/profile.demo.json) 和 [完整实施计划](从零到一实施计划.md) 第 7 节。

准备好真实履历后，打开已登录的招聘表单，先点「扫描页面」检查识别，再点「一键填写」，核对结果。即使站点已有专用适配器，页面版本和公司配置仍可能不同，复杂区域需要人工补齐。

## 9. 备份与更新

工作台「备份」→「导出完整备份」可以保存履历、字段规则和投递记录。完整备份是保存在自己电脑上的明文 JSON。

「投递记录」→「导出 CSV」适合在表格软件查看和迁移记录摘要。CSV 不代替完整备份。

「恢复备份」会用文件内容替换整个当前数据，操作前先导出现有备份。

代码修改完成后，在终端执行：

```bash
cd /path/to/ApplyKit
npm run build
```

然后：

1. 在 `chrome://extensions` 点击投简助手卡片上的「重新加载」。
2. 先保存招聘页面未保存的进度，再刷新目标网页。
3. 再次点击工具栏图标并填写。

不需要反复卸载重装。卸载会删除扩展本地数据；保持安装目录不变，并定期备份。

## 10. 常见情况

| 现象 | 处理方式 |
| --- | --- |
| 「一键填写」不可点击 | 先导入并选中履历，再回到普通 http/https 网页点击工具栏图标 |
| 提示无权限访问页面 | 切回目标页重新点击图标；跨站跳转后需要重新授权 |
| 本地网址打不开 | 确认 `npm run demo` 的终端仍在运行且使用端口 4173 |
| 提示虚构资料只能在本地使用 | 换成独立整理并审阅过的真实履历，不能直接使用演示数据 |
| 待处理很多 | 查看各项原因；未知标签可手动对应，控件不支持或事实缺失则手动处理 |
| 内容已填但记录不是已投递 | 这是正常流程，需要网站实际提交成功后由你确认 |
| 刷新后旧结果无法定位或重试 | 原页面节点已失效，回到网页重新扫描 |
| 修改源码后没有变化 | 重新 build、重新加载扩展，并刷新目标网页 |
| 导入旧 JSON 失败 | 当前只接受 ApplyKit 原生履历格式；先转换，不更改原文件冒充格式 |

## 11. 建议的第一次体验顺序

先跑 `basic`，确认安装和当前页面授权；再跑 `experience`，检查多段经历；最后跑 `edge-cases`，体验字段修正与复用。最后保存一条演示投递记录并导出备份。

这几步完成后，再整理真实履历并选择一个实际会投的网站试用。发现问题时记录页面类型、字段名、期望行为和实际行为，交给开发 AI 修复；提供样例时移除个人信息。
