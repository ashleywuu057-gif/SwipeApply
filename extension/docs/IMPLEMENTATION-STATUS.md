## 与计划书的差异（已实现但做法不同）

1. **重复经历绑定放在后台，而不是内容脚本里的 `bindRecords`。**
   计划书的 `SiteAdapter` 接口把 `bindRecords(section, profile)` 放在适配器里，那需要把履历记录摘要（学校名、公司名）发进网页所在的内容脚本。这里改成：内容脚本只回传页面上真实存在的线索（学历标注、已填名称、容器顺序），后台用 `src/shared/matching.ts` 的 `bindRecords` 完成绑定。语义与优先级与计划书一致，但内容脚本拿不到履历内容。

2. **新增了 `ADD_RECORDS` 与 `LIST_TARGET_TABS` 两个消息。**
   计划书写的是「协议至少包括」下列消息。`ADD_RECORDS` 用来在新增经历后重新扫描并重新生成计划；`LIST_TARGET_TABS` 让工作台页面选择目标标签页（生产环境没有 host 权限时它只能看到 activeTab 授权过的页面，权限仍由 Chrome 强制）。

3. **后台自身的运行报告写入不推进 `revision`。**
   `revision` 用于阻止两个界面互相覆盖用户编辑。运行报告是后台记账，如果它也推进版本号，任何一次填写都会让已打开的工作台页面失效。`mutate({bumpRevision:false})` 只用于运行报告与中断标记。

4. **增加了一次「异步校验复查」。**
   有些网站在写入之后才异步把字段标成无效。执行器在整轮动作结束后等待 400ms，复查所有已填字段的 `aria-invalid` 与原生 validity，发现错误就把结果降级为 `failed / VALIDATION_FAILED`，避免谎报成功。

5. **`bindRecords` 增加了「唯一容器 ↔ 唯一记录」规则。**
   计划书列了适配器 → 身份 → 用户 → 固定顺序四步。当页面只有一个容器、履历也只剩一条可用记录时，对应关系是被证明的而不是猜的，因此直接绑定（reason = `unique`）。仍然不会在「一个容器、两条候选记录」时按顺序猜测。

6. **网页上已有名称但履历里没有同名记录时，该容器整体待处理。**
   计划书要求「网页记录多于履历、重复身份或结构含糊时保留并报告」。实现上把这类容器直接标为 `AMBIGUOUS_RECORD`，避免把别的经历填进一个已经写着别人名字的区块。

7. **支持了计划书 P0 之外的自定义下拉。**
   计划书第 3.1 节把自定义控件限定为「有明确 ARIA 关系的 combobox」。实测发现国内 ATS 的下拉普遍没有任何
   ARIA，按 P0 原样交付等于在真实网站上几乎不可用。因此新增了结构化通道，安全边界与 ARIA 版本完全一致：
   只在控件自己的下拉容器内找选项（绝不全页搜索）、只接受唯一精确匹配、点击后必须回读确认、
   找不到就把控件恢复原样并如实报告。日期选择器（日历结构）仍然一律不碰。

8. **`FieldDescriptor` 增加了 4 个字段。**
   `datePart`（分拆年/月控件的角色）、`degreeHint`（页面标注的学历层级）、`recordIdentityHint`（页面已填的记录名称）、`unsupportedReason`（不支持控件的具体原因，用于在结果页显示「附件需要你自己上传」而不是只有错误码）。计划书第 9.1 节的字段全部保留，语义未变。
